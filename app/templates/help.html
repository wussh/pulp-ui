How to use this console

This console replaces the ad-hoc scripts/pulp/*.py workflow. It owns no state: Pulp remains the source of truth for every resource. The activity records it keeps live in memory only and vanish when the pod restarts.

The pages, in workflow order

The navigation follows the order an operator actually works in.

Overview

Read this first. It reports whether the internal Pulp API is reachable, the pulpcore version, the public route status, and counts of domains, container repositories and distributions, active tasks, and failed tasks.

A yellow pulp.failed_tasks warning means Pulp has failed tasks — go to Tasks and filter by state failed. Everything here is read-only.

Tenants

Shows domains, users, and groups, and drives guided tenant setup.

Setup is preview then apply, never one step:

  1. Fill in Domain, Username, and Group.
  2. Click Preview. The server reports each planned step as create or reuse against what already exists.
  3. Read any probe_warnings. A warning means a lookup did not complete cleanly, so the plan may be optimistic about what already exists. Fix the cause before applying.
  4. Click Apply — now enabled.

Apply submits the steps in order and stops at the first failure. There is no automatic rollback. The response lists the resources that were completed, the step that failed, and a recovery string explaining what to do next.

That recovery text is deliberately specific about what this UI cannot undo: domains, users, and groups cannot be deleted from the delete page, so it names the Pulp API as the way to remove them. Re-running Apply is safe — it re-fetches current state and performs only the steps still missing.

Content

Lists repositories and distributions per plugin (RPM, DEB, Python, Ansible, Container), filtered by domain, and provides three forms.

FormFieldsNotes
Create repository domain, plugin, name Returns a pulp_href — keep it
Create distribution domain, plugin, name, repository href, base path base_path is required for container only
Sync repository domain, plugin, repository href, remote URL, remote name URL must be https and the host must be on the allowlist

The repository-href field must be a full record href from the same domain and plugin. The server rejects a foreign domain's href and a collection-level href with 400.

A new repository needs a distribution before clients can consume it. For an RPM repository that is a two-step flow: create the repository, copy the returned href, then create a distribution pointing at it.

If Sync returns a task_href, the browser navigates to the task detail page automatically so you can watch progress.

Per-plugin failures are isolated. If one plugin's endpoint fails, the page still loads the others and prints a warning naming the plugin that failed. The page only errors when every plugin fails. Treat a plugin warning as "this plugin's data is missing from this view", not as "Pulp is down".

Tasks

Lists Pulp tasks filtered by domain and state (running, waiting, completed, failed, canceled, skipped). Click open on a row for detail.

The detail page polls every two seconds while the task is unfinished and stops on a terminal state. It shows progress reports, the resources the task created, and — on failure — a bounded error summary.

Validation

Runs the tenant-isolation check against a domain. It reports three assertions, each PASS or FAIL with evidence: domain_isolation, resource_creation, and resource_listing.

The check creates a uniquely named test resource, then cross-reads a different domain and asserts the created href is absent there. That ordering is deliberate: an isolation assertion that reads before creating can never fail, which is worse than no assertion. It also means a FAIL may leave one disposable resource behind — the response returns a run_id, and POST /ui/api/validation/cleanup with that id deletes only the hrefs that run recorded.

If the cross-domain search hits its page cap, the assertion reports FAIL with a "truncated" note rather than PASS. A truncated search cannot prove isolation.

Activity

The in-process record of what this pod has done: timestamp (UTC), operator, action, target type and identifier, result, and correlation ID.

These records live in memory only. A pod restart clears them. They are not an audit log and should not be used as one. Use the correlation ID to find the matching server logs: 

kubectl -n pulp logs deploy/pulp-ops | grep <correlation-id>

Worked example — publishing an RPM repository

  1. Overview — confirm Pulp is reachable and no failed-task warning is showing.
  2. Content — Domain default, Plugin rpm, Name <repo-name> → Create. The output shows the new pulp_href.
  3. Copy that href.
  4. Content — in Create distribution, paste it into Repository href, give the distribution a name → Create.
  5. Tasks — watch the task reach completed.
  6. Content — the repository now appears under the rpm section.

Deleting a resource

Deletion is not in the navigation. Open /ui/delete directly. The flow is layered on purpose:

  1. Enter the domain and the exact resource href.
  2. Click Preview. This is required, not decorative — it fetches the resource and shows its current type, name, domain, and href, plus a dependency warning.
  3. Read the dependency warning:
    • Referenced by: ... — something still uses this resource.
    • No dependencies recorded — nothing references it.
    • Dependency check could not complete: ... — the lookup failed. Do not read this as "no dependencies." The answer is unknown.
  4. Tick the confirmation checkbox.
  5. Click Delete.

Without the tick the server returns 400 and issues no delete. The gate is enforced server-side, so disabling JavaScript or posting directly does not bypass it.

Only plugin-scoped resources are deletable here — repositories, distributions, remotes, tasks. Domains, users, and groups are not: their hrefs are rejected by design. Remove those through the Pulp API.

Consuming the repositories

How to pull from the repositories this Pulp serves. Every URL below was verified against the live server — the HTTP status is stated for each. Replace default with your tenant's domain when you are not using the shared one.

RPM (dnf / yum)

# /etc/yum.repos.d/pulp.repo
[pulp-rocky9-baseos]
name=Pulp rocky9-baseos
baseurl=https://pulp.dev.tbs.cloudeka.xyz/pulp/content/default/rpm/rocky9-baseos/
enabled=1
gpgcheck=0
sudo dnf clean all && sudo dnf repolist
sudo dnf install <package>

Verified: GET /pulp/content/default/rpm/rocky9-baseos/repodata/repomd.xml → 200, no authentication. Other RPM distributions: rpm/rocky9-appstream, rpm/epel9 — swap the last path segment.

DEB (apt)

echo "deb [trusted=yes] https://pulp.dev.tbs.cloudeka.xyz/pulp/content/default/deb/ubuntu-noble/ noble main" \
  | sudo tee /etc/apt/sources.list.d/pulp.list
sudo apt update && sudo apt install <package>

Verified: GET /pulp/content/default/deb/ubuntu-noble/dists/noble/Release → 200, no authentication. Also available: deb/ubuntu-jammy. [trusted=yes] is required because the repository is not GPG-signed — keep it only if you accept that trade-off.

Python (pip)

pip install --index-url https://pulp.dev.tbs.cloudeka.xyz/pulp/content/default/python/pypi/simple/ <package>

Persist it in ~/.pip/pip.conf:

[global]
index-url = https://pulp.dev.tbs.cloudeka.xyz/pulp/content/default/python/pypi/simple/
trusted-host = pulp.dev.tbs.cloudeka.xyz

Verified: GET /pulp/content/default/python/pypi/simple/ → 200, no authentication.

Ansible Galaxy (ansible-galaxy)

This one does not live under /pulp/content/. Ask Pulp for the distribution's own client_url and use that — do not guess the path: 

curl -s -u admin:'<admin-password>' \
  'https://pulp.dev.tbs.cloudeka.xyz/pulp/default/api/v3/distributions/ansible/ansible/' \
  | python3 -c "import json,sys; [print(r['name'], r['client_url']) for r in json.load(sys.stdin)['results']]"

On this cluster that returns https://pulp.dev.tbs.cloudeka.xyz/pulp_ansible/galaxy/default/ansible/galaxy/, so: 

ansible-galaxy collection install <namespace>.<collection> -c \
  -s https://pulp.dev.tbs.cloudeka.xyz/pulp_ansible/galaxy/default/ansible/galaxy/

# or persistently, in ansible.cfg
[galaxy]
server_list = pulp

[galaxy_server.pulp]
url = https://pulp.dev.tbs.cloudeka.xyz/pulp_ansible/galaxy/default/ansible/galaxy/

Verified: the galaxy API root /pulp_ansible/galaxy/default/ansible/galaxy/api/ answers 200 without credentials, while content endpoints answer 401 — so some operations need username/password in the server block.

Container images (docker / podman)

The registry uses a different path shape and a different service than the package content: /v2/<domain>/<distribution base_path>. The base path itself contains slashes. 

docker login pulp.dev.tbs.cloudeka.xyz

docker pull pulp.dev.tbs.cloudeka.xyz/v2/default/dockerhub/library/alpine:latest
docker pull pulp.dev.tbs.cloudeka.xyz/v2/default/quay/prometheus/prometheus:latest

Verified: GET /v2/ answers 401 with WWW-Authenticate: Bearer realm="https://pulp.dev.tbs.cloudeka.xyz/token/" — the standard registry challenge. That 401 is the proof the registry is alive; a 404 would mean the path is wrong. A client that authenticates against the advertised realm receives a bearer token and then pulls.

Registry base paths here: dockerhub/library/{alpine,nginx,busybox}, quay/prometheus/prometheus, quay/containerdisks/{centos-stream,ubuntu}, quay/kubevirt/cirros-container-disk-demo.

Things that surprise people

  • Task operations are asynchronous. An empty-looking result usually means the task is still running. Check Tasks before concluding something failed.
  • Preview is load-bearing for tenant Apply and for Delete. Both exist because the operation that follows is hard to undo.
  • Activity is not durable. It is a debugging aid for the current pod, nothing more.
  • The Content page can be partially populated. A per-plugin warning is a gap in one plugin's data, not a failed page.
  • A dependency check that fails is not a dependency check that passed. The three states are distinguished deliberately.
