How to use this console

This console replaces most of the ad-hoc scripts/pulp/*.py workflow. It owns no state: Pulp remains the source of truth for every resource. The activity records it keeps live in memory only and vanish when the pod restarts. Every operation the old scripts/pulp/*.py set performed is now available from a page — see These operations are now in the UI.

The pages, in workflow order

The navigation follows the order an operator actually works in.

Overview

Read this first. It reports whether the internal Pulp API is reachable, the pulpcore version, the public route status, and counts of domains, container repositories and distributions, active tasks, and failed tasks.

A yellow pulp.failed_tasks warning means Pulp has failed tasks — go to Tasks and filter by state failed. Everything here is read-only.

Tenants

Shows domains, users, and groups, and drives guided tenant setup.

Setup is preview then apply, never one step:

  1. Fill in Domain, Username, and Group.
  2. Click Preview. The server reports each planned step as create or reuse against what already exists.
  3. Read any probe_warnings. A warning means a lookup did not complete cleanly, so the plan may be optimistic about what already exists. Fix the cause before applying.
  4. Click Apply — now enabled.

Apply submits the steps in order and stops at the first failure. There is no automatic rollback. The response lists the resources that were completed, the step that failed, and a recovery string explaining what to do next.

That recovery text is deliberately specific about what this UI cannot undo: domains, users, and groups cannot be deleted from the delete page, so it names the Pulp API as the way to remove them. Re-running Apply is safe — it re-fetches current state and performs only the steps still missing.

Role assignments has its own lookup: enter a domain and group and click Look up to see the group's current assignments.

Content

Lists repositories and distributions per plugin (RPM, DEB, Python, Ansible, Container), filtered by domain, and provides three forms.

FormFieldsNotes
Create repository domain, plugin, name Returns a pulp_href — keep it
Create distribution domain, plugin, name, repository href, base path base_path is required for container only
Sync repository domain, plugin, repository href, remote URL URL must be https and the host must be on the allowlist

The repository-href field must be a full record href from the same domain and plugin. The server rejects a foreign domain's href and a collection-level href with 400.

A new repository needs a distribution before clients can consume it. For an RPM repository that is a two-step flow: create the repository, copy the returned href, then create a distribution pointing at it.

If Sync returns a task_href, the browser navigates to the task detail page automatically so you can watch progress.

Per-plugin failures are isolated. If one plugin's endpoint fails, the page still loads the others and prints a warning naming the plugin that failed. The page only errors when every plugin fails. Treat a plugin warning as "this plugin's data is missing from this view", not as "Pulp is down".

Tasks

Lists Pulp tasks filtered by domain and state (running, waiting, completed, failed, canceled, skipped). Click open on a row for detail.

The detail page polls every two seconds while the task is unfinished and stops on a terminal state. It shows progress reports, the resources the task created, and — on failure — a bounded error summary.

Validation

Runs the tenant-isolation check against a domain. It reports two phases, each assertion PASS or FAIL with evidence.

Admin phase. Authenticated as the Pulp admin, it creates a uniquely named test resource, then cross-reads a different domain and asserts the created href is absent there. Assertions: domain_isolation, resource_creation, resource_listing. The ordering is deliberate: an isolation assertion that reads before creating can never fail, which is worse than no assertion.

Tenant phase. When a non-superuser credential is stored for the domain, the check runs a second time as that tenant and reports tenant_isolation (the tenant cannot read the other domain's listing) and tenant_own_listing (the tenant can read its own). This is the phase that proves confinement: admin sees every domain, so the admin phase alone only proves a resource is absent from a listing. With no credential stored, the result says so explicitly — it does not pass the admin check off as isolation.

A FAIL may leave one disposable resource behind — the response returns a run_id, and POST /ui/api/validation/cleanup with that id deletes only the hrefs that run recorded.

If a cross-domain search hits its page cap, the assertion reports FAIL with a "truncated" note rather than PASS. A truncated search cannot prove isolation.

Cluster Secrets

Applies pulp-s3-credentials and pulp-postgres-credentials from the same sources as the old setup-secrets.sh, and shows which Secrets exist and which keys they carry. Only names and key names are ever displayed. The Postgres username and password are read from everest-secrets-db-pulp in the prod namespace; a missing source Secret is reported, not faked.

Activity

The in-process record of what this pod has done: timestamp (UTC), operator, action, target type and identifier, result, and correlation ID.

These records live in memory only. A pod restart clears them. They are not an audit log and should not be used as one. Use the correlation ID to find the matching server logs: 

kubectl -n pulp logs deploy/pulp-ops | grep <correlation-id>

Configuring Pulp from this UI

Task-first: pick the thing you want and run the flow. Every mutation below fires a Pulp task; the browser follows it to the Tasks page so you can watch it. Nothing here waits inline — a long publish does not hold a request open.

Add an RPM or DEB repository

RPM and DEB need a publication before the distribution can serve content. The whole chain is available on Content:

  1. Create repository — set domain, plugin rpm or deb, and a name. Copy the returned pulp_href.
  2. Create distribution — paste the repository href, give the distribution a name. Leave Base path empty — it applies to container only.
  3. Sync repository — paste the repository href and the upstream URL. The URL must use https and its host must be on the server's allowlist. The sync runs as a task; watch it on Tasks.
  4. Publish repository — paste the repository href. The UI reads the repository's latest version and starts the publication. Copy the resulting publication href.
  5. Link distribution to publication — paste the distribution href and the publication href. This rebinds the distribution from the repository to the publication, which is what makes RPM and DEB content actually serve.

DEB publish is slow: ubuntu-noble takes roughly 25 minutes. The UI does not time out waiting for it — it fires the task and you follow it on Tasks. Do not conclude the publish failed because it is still running an hour later.

Add a container registry (pull-through)

Container has no repository or sync step — it is a pull-through cache. On Content, the existing registries are listed in the Container pull-through registries table with their upstream URL. To add one, use Add pull-through registry: domain, a name, a base path, and the upstream URL. The upstream host must be on the allowlist.

The UI creates two objects in one step: the pull-through remote under the name you gave, and a distribution named <name>-proxy carrying base_path and the remote. Clients pull from /v2/<domain>/<base_path>/....

Set up a tenant and its roles

Tenants → Guided tenant setup creates the domain, the user, the group, and assigns the full role set in one idempotent run. Fill in Domain, Username, and Group, click Preview, then Apply.

The role step grants core.domain_owner and core.domain_creator plus, for each of RPM, DEB, Python, Ansible, and Container, both the *_creator and *_owner role. Both are required: a group with only *_owner gets 403 when it tries to create anything in its own domain. The grants are model-level — they cover every object already in the domain and every object created there later.

Re-running Apply is safe: it re-fetches current state and performs only the missing steps. Check what a group already has with the Role assignments lookup.

The domain is created with its custom S3-backed storage: the UI sends storage_class and storage_settings from the S3 credential the pod holds. Supply an optional Description, and an optional Bucket override if this tenant needs its own bucket rather than the shared default. The S3 keys are never entered in the browser and never returned.

Add a Python package

Python has no pull-through: only packages named in the remote's includes list are served. On Content → Python package includes, enter the domain, the remote href, the repository href, and the package names as a comma-separated list, then click Merge and sync. The UI unions your names with the existing list, patches the remote, and starts the sync. Adding nothing new is a no-op: it reports changed: false and fires no empty sync.

Add an Ansible collection

Ansible is the same shape as Python: only collections in the remote's requirements_file are served, and there is no publish step — the distribution serves straight from the repository. On Content → Ansible collections, enter the domain, remote href, repository href, and collection names as namespace.name comma-separated, then click Merge and sync.

The merge edits the operator's own requirements document: comments, blank lines, and other top-level keys survive untouched, and only the collections: block is rewritten. A requirements file the UI cannot parse is refused rather than overwritten. An empty requirements file is likewise refused — see the OOM warning under Things that surprise people.

Worked example — publishing an RPM repository

  1. Overview — confirm Pulp is reachable and no failed-task warning is showing.
  2. Content — Domain default, Plugin rpm, Name <repo-name> → Create. The output shows the new pulp_href.
  3. Copy that href.
  4. Content — in Create distribution, paste it into Repository href, give the distribution a name → Create.
  5. Content — in Sync repository, paste the same href and the upstream https URL → Sync. The browser follows the task.
  6. Tasks — watch the sync reach completed.
  7. Content — Publish repository with the repository href, then Link distribution to publication with the distribution and publication hrefs.
  8. Content — the repository now appears under the rpm section.

Deleting a resource

Deletion is not in the navigation. Open /ui/delete directly. The flow is layered on purpose:

  1. Enter the domain and the exact resource href.
  2. Click Preview. This is required, not decorative — it fetches the resource and shows its current type, name, domain, and href, plus a dependency warning.
  3. Read the dependency warning:
    • Referenced by: ... — something still uses this resource.
    • No dependencies recorded — nothing references it.
    • Dependency check could not complete: ... — the lookup failed. Do not read this as "no dependencies." The answer is unknown.
  4. Tick the confirmation checkbox.
  5. Click Delete.

Without the tick the server returns 400 and issues no delete. The gate is enforced server-side, so disabling JavaScript or posting directly does not bypass it.

Only plugin-scoped resources are deletable here — repositories, distributions, remotes, tasks. Domains, users, and groups are not: their hrefs are rejected by design. Remove those through the Pulp API.

Consuming the repositories

How to pull from the repositories this Pulp serves. Every URL below was verified against the live server — the HTTP status is stated for each. Replace default with your tenant's domain when you are not using the shared one.

RPM (dnf / yum)

# /etc/yum.repos.d/pulp.repo
[pulp-rocky9-baseos]
name=Pulp rocky9-baseos
baseurl=https://pulp.dev.tbs.cloudeka.xyz/pulp/content/default/rpm/rocky9-baseos/
enabled=1
gpgcheck=0
sudo dnf clean all && sudo dnf repolist
sudo dnf install <package>

Verified: GET /pulp/content/default/rpm/rocky9-baseos/repodata/repomd.xml → 200, no authentication. Other RPM distributions: rpm/rocky9-appstream, rpm/epel9 — swap the last path segment.

DEB (apt)

echo "deb [trusted=yes] https://pulp.dev.tbs.cloudeka.xyz/pulp/content/default/deb/ubuntu-noble/ noble main" \
  | sudo tee /etc/apt/sources.list.d/pulp.list
sudo apt update && sudo apt install <package>

Verified: GET /pulp/content/default/deb/ubuntu-noble/dists/noble/Release → 200, no authentication. Also available: deb/ubuntu-jammy. [trusted=yes] is required because the repository is not GPG-signed — keep it only if you accept that trade-off.

Python (pip)

pip install --index-url https://pulp.dev.tbs.cloudeka.xyz/pulp/content/default/python/pypi/simple/ <package>

Persist it in ~/.pip/pip.conf:

[global]
index-url = https://pulp.dev.tbs.cloudeka.xyz/pulp/content/default/python/pypi/simple/
trusted-host = pulp.dev.tbs.cloudeka.xyz

Verified: GET /pulp/content/default/python/pypi/simple/ → 200, no authentication.

Ansible Galaxy (ansible-galaxy)

This one does not live under /pulp/content/. Ask Pulp for the distribution's own client_url and use that — do not guess the path: 

curl -s -u admin:'<admin-password>' \
  'https://pulp.dev.tbs.cloudeka.xyz/pulp/default/api/v3/distributions/ansible/ansible/' \
  | python3 -c "import json,sys; [print(r['name'], r['client_url']) for r in json.load(sys.stdin)['results']]"

On this cluster that returns https://pulp.dev.tbs.cloudeka.xyz/pulp_ansible/galaxy/default/ansible/galaxy/, so: 

ansible-galaxy collection install <namespace>.<collection> -c \
  -s https://pulp.dev.tbs.cloudeka.xyz/pulp_ansible/galaxy/default/ansible/galaxy/

# or persistently, in ansible.cfg
[galaxy]
server_list = pulp

[galaxy_server.pulp]
url = https://pulp.dev.tbs.cloudeka.xyz/pulp_ansible/galaxy/default/ansible/galaxy/

Verified: the galaxy API root /pulp_ansible/galaxy/default/ansible/galaxy/api/ answers 200 without credentials, while content endpoints answer 401 — so some operations need username/password in the server block.

Container images (docker / podman)

The registry uses a different path shape and a different service than the package content: /v2/<domain>/<distribution base_path>. The base path itself contains slashes. 

docker login pulp.dev.tbs.cloudeka.xyz

docker pull pulp.dev.tbs.cloudeka.xyz/v2/default/dockerhub/library/alpine:latest
docker pull pulp.dev.tbs.cloudeka.xyz/v2/default/quay/prometheus/prometheus:latest

Verified: GET /v2/ answers 401 with WWW-Authenticate: Bearer realm="https://pulp.dev.tbs.cloudeka.xyz/token/" — the standard registry challenge. That 401 is the proof the registry is alive; a 404 would mean the path is wrong. A client that authenticates against the advertised realm receives a bearer token and then pulls.

Registry base paths here: dockerhub/library/{alpine,nginx,busybox}, quay/prometheus/prometheus, quay/containerdisks/{centos-stream,ubuntu}, quay/kubevirt/cirros-container-disk-demo.

These operations are now in the UI

There is no longer a script-only task. Each operation the old script set performed is available on a page, and the credentials behind them are held by the UI process rather than typed into a browser form.

TaskPage
Create a domain with custom storage Tenants → Guided tenant setup. The domain is created with its storage_class and storage_settings from the S3 credential the pod holds. You supply the domain name, an optional description, and an optional bucket override; the S3 keys are never entered in the browser and never returned.
Apply the S3 and Postgres Secrets to the cluster Cluster Secrets (/ui/secrets). Applies pulp-s3-credentials and pulp-postgres-credentials from the same sources the old shell script used, and shows which Secrets exist and which keys they carry. No value is ever displayed.
Prove cross-tenant isolation with real tenant credentials Tenants → Tenant credential stores a non-superuser credential for a domain; Validation then runs a second phase authenticated as that tenant, asserting it cannot read another domain's listing and can read its own. The assertions are named tenant_isolation and tenant_own_listing. With no credential stored, the result says so and does not pass the admin check off as isolation.

Honest framing on credentials. This UI already held the Pulp admin credential, so "credentials must not be held by the UI process" was never true. It now holds more of them. They are guarded by RBAC scoped to specific Secret names — a strict allowlist in the application refuses any other name before a request is made — and no value is ever returned to the browser, logged, or written to an activity record.

Everything else the old script set did — creating and syncing repositories, publishing, linking, adding registries, editing Python includes and Ansible collections, creating domains, and assigning tenant roles — is also done from the pages above.

Sync policy — on_demand vs immediate

Policy is set on the remote, not on the repository. on_demand syncs metadata and fetches a file only when a client asks for it; immediate downloads every file during the sync.

on_demandimmediate
Sync speedFastSlow (downloads everything)
Storage after syncSmall (metadata only)Large (all files)
Client pull speedFetches from upstream on first request, then cachesAlways from local cache
Best forDefault — saves storageAir-gapped, or no internet at runtime
Full RPM storage estimate~500 MB metadata~30–50 GB
Full DEB storage estimate~1 GB metadata~200 GB+

Ansible caveat: remotes/ansible/collection does not support on_demand — only immediate and streamed. Its default is immediate, and that is safe: it downloads collection metadata, not binaries.

The UI's Sync form does not expose the policy field. A sync from the Content page creates a one-off remote and syncs with it, so it uses whatever default the plugin applies. To pin a repository to immediate, either run the plugin's setup script with "policy": "immediate" on the remote, or PATCH the existing remote's policy through the Pulp API and re-sync.

Maintenance

These operate below the UI — an API call or the database. A reader should copy them exactly.

Orphan cleanup

Run after a failed sync or a repository deletion. This has no UI trigger; fire it against the API, then watch the task on Tasks. It can take 30–60 minutes when there is a lot to remove. 

kubectl --kubeconfig kubeconfig/kubeconfig-tbs-dev.yaml \
  exec -n pulp deploy/pulp-api -- python3 -c "
import urllib.request, json, base64
H = {'Authorization': 'Basic ' + base64.b64encode(b'admin:').decode()}
body = json.dumps({'orphan_protection_time': 0}).encode()
req = urllib.request.Request('http://localhost:24817/pulp/api/v3/orphans/cleanup/',
    data=body, headers={**H, 'Content-Type': 'application/json'}, method='POST')
print(json.loads(urllib.request.urlopen(req).read()))
"

pgbackrest — manual base backup

kubectl --kubeconfig kubeconfig/kubeconfig-tbs-dev.yaml \
  exec -n prod db-pulp-repo-host-0 -c pgbackrest -- \
  pgbackrest backup --stanza=db --type=full

Run this after a large sync (a lot of new data) to enable WAL pruning.

Check the database disk

kubectl --kubeconfig kubeconfig/kubeconfig-tbs-dev.yaml \
  exec -n prod db-pulp-instance1-dqbq-0 -c database -- df -h /pgdata

Things that surprise people

  • Task operations are asynchronous. An empty-looking result usually means the task is still running. Check Tasks before concluding something failed.
  • Preview is load-bearing for tenant Apply and for Delete. Both exist because the operation that follows is hard to undo.
  • Activity is not durable. It is a debugging aid for the current pod, nothing more.
  • The Content page can be partially populated. A per-plugin warning is a gap in one plugin's data, not a failed page.
  • A dependency check that fails is not a dependency check that passed. The three states are distinguished deliberately.
  • The Overview storage "100%" is a false alarm. It shows Total: 0 bytes, Free: 0 bytes because the RustFS S3 backend does not report capacity to the Pulp API — it returns total: null and free: null, and the UI renders null as 0. Actual usage has been around 1–2 GiB. To see the real number, read used from the status API inside the api pod: 
    kubectl --kubeconfig kubeconfig/kubeconfig-tbs-dev.yaml \
  exec -n pulp deploy/pulp-api -- python3 -c "
import urllib.request, json, base64
H = {'Authorization': 'Basic ' + base64.b64encode(b'admin:').decode()}
with urllib.request.urlopen(urllib.request.Request(
    'http://localhost:24817/pulp/api/v3/status/', headers=H)) as r:
    print(json.loads(r.read())['storage'])
"
    It prints something like {'total': null, 'used': 1110292962, 'free': null} — used is in bytes, about 1.1 GiB.
  • DEB publishing is slow. ubuntu-noble takes roughly 25 minutes. The UI fires the task and follows it; it does not sit and wait. Budget for it rather than assuming a hang.
  • An empty Ansible requirements_file will OOM the worker. A sync with no requirements file downloads the whole of galaxy.ansible.com. The UI's Ansible form refuses to sync when the merged requirements would be empty, and the merge preserves whatever else is in the file. Never blank that field to "start clean".
  • Validation's admin phase is weaker than the tenant phase. The domain_isolation assertion runs as the admin superuser, so it proves absence from a listing, not tenant confinement. Store a tenant credential on Tenants and the tenant_isolation assertion supplies the stronger proof. Without one, the result says isolation was not verified as a tenant.
